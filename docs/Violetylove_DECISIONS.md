## 1. 查看大模型的输入、输出 —— 一击命中，暴露真相（2026-08-22）

### 背景

Gmail 跨应用发信任务反复失败：模型能填入收件人 `violetylove@163.com`，却始终无法继续填
主题/正文/发送。此前一段时间内，我曾误判为 "Gmail 主题/正文不在无障碍树（采集缺失）"，
并一度考虑「更换云端模型」或「UI 采集引入模型视觉」——方向有可能走上歧途。

### Violetylove 的英明决断

Violetylove 主动提出并坚持：**不要猜，直接查看大模型的输入与输出**（每一轮发给模型的
`ui_xml` 摘要，以及模型返回的原始回复含思考与指令）。为此临时增强诊断日志（DIAG）：记录
每轮请求 UI 是否含 `建议/主题/正文/收件人`，并记录模型原始回复。

### 结果：真相一次性暴露

- **模型看到了什么**：DIAG 显示第 4、5 轮 UI 里 `has_subject=True`、`has_body=True`。
  **注意**：`has_subject`/`has_body` 是用 `"主题"/"正文" in ui_xml` 做的**原始 XML 字符串字面匹配**，
  只反映 XML 里**出现了"主题/正文"字样**（placeholder/desc），**不代表**模型经 `summarize_xml`
  拿到了可交互的主题/正文输入框节点。即"字面命中"≠"模型可操作"。这正是此前一度误判为
  "主题/正文可见、问题不大"的原因——真实模型拿到的是**过滤后的可交互节点**，其中未必有主题/正文。
- **模型如何回复**：第 6 轮模型思考明确 "下一步需要填写主题，因此点击主题输入框"，
  指令 `click node 13`——**模型规划方向正确**，一路走到"该填主题"。
- **真正的问题（第 6 轮后停住）**：`click node 13` 执行后未产生后续请求，疑似主题框节点
  被突发建议组件错位/遮挡导致点击落空，触发执行失败收敛。

### 补充：更根本的发现（session 95ef56ff）

重新测试（Gmail 已重置）发现**比建议组件更前置的问题**：模型点开 Gmail 后，下一轮传给
模型的 `ui_bytes=0`、`DIAG nodes count=0`（**空 UI**），且 app 仍是 `nexuslauncher`——
模型拿到的界面为空，只能输出 `wait`。这说明**执行层在动作后采集 UI 树的时机/新鲜度**：
点开关口后新窗口无障碍尚未就绪，采到空/旧树，模型根本看不到界面。
可能原因与「建议组件出现后模型未拿到新 UI 树」是同类——执行层采集时机/新鲜度问题。

### 关键价值

1. **避免歧途**：无需更换大模型，也无需在 UI 采集时引入模型视觉——问题不在模型智力，
   也不在采集缺节点，而在执行层的点击目标被突发建议组件错位。
2. **证明方法**：**查看模型的输入、输出**是定位这类"模型会做但执行卡住"问题的最高效手段，
   比反复猜模型能力、改提示词措辞、换模型都更直接。

## 2. 待排查事项（Violetylove 提出）

- **第 6 轮 node 13 的实际含义**：确认模型该轮拿到的 UI 树里 `node 13` 到底是什么
  （是否真是主题框，还是被建议卡挤占的容器/错位节点），以定位点击落空根因。

- **突发建议组件为何模型没看到新 UI 树**：填入收件人后建议组件弹出，但模型下一步似乎
  基于旧树决策、没感知到新组件。需要排查：建议组件出现是否伴随 UI 树更新事件、模型
  是否拿的是过期树（关联观察新鲜度/重采机制）。
  - 可能涉及：新增"突发情况处理"——用户意图未完成、模型未返回结束标志时，**强制重新
    获取界面 UI 树**，避免模型一直用旧树决策。

---

### 最终判断

- 不是模型不会填主题，也不是点错节点——**主题/正文输入框在建议组件出现的那一刻，
  未被采集为可交互节点（被遮挡/未暴露**），模型点它们无效、界面不变。
- 这正回到 **Violetylove 的判断**：**弹出建议组件后，没有把新的 UI 树信息（含被遮挡的主题框）
  正确采集并送给模型**；执行层"界面已更新"的判断逻辑需要优化，才能在建议组件出现后仍把
  主题框作为可点击节点暴露给模型。
